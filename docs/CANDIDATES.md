# 追加候補の保存と辞書への反映

2026-10-13から、ブラウザアプリは候補用の別DBに保存する運用です。名前・読み・別の変換・判断・メモを保存し、辞書への追加はCodexへ別途依頼します。

## 保存先と操作の違い

| 操作・場所 | 内容 |
| --- | --- |
| アプリの「追加する」や入力の自動保存 | 今の作業記録に追加予定・編集内容を保存する |
| アプリの「候補DBに保存する」 | 確認した判断・編集内容を候補DBに保存する |
| `outputs/vtuberpost_private/` | 候補DB。主一覧・別管理候補・判断・別の変換・編集履歴を保持する |
| `data/master.tsv` | 配布辞書の編集元。候補DBを確認したうえで、別の作業として追加する |
| `dist/`・`data/additions.tsv` | `master.tsv` から生成する配布ファイルと追加記録 |
| `public/` | ローカルに生成した検索サイト・検索データ・ZIP |
| Gitのコミット | 作業ブランチに辞書や説明の変更を記録する |
| Web公開 | 本番ブランチへの反映と公開処理を行い、公開結果を確認する |
| 各IMEへのインポート | 配布辞書をIMEに取り込む操作。アプリの保存やWeb公開とは別に行う |

候補DBで「採用」になっていても、辞書への登録状況は別途確認が必要です。過去に追加した候補も追加予定の一覧に残るため、各「読み・名前」の組み合わせを `master.tsv` と照合します。

アプリの「参照中の辞書」の語数と、呼び出し一覧の辞書登録表示は、プロジェクト内の `master.tsv` を参照した情報です。公開サイトや、このPCのIMEへの取り込み状況を示すものではありません。呼び出し一覧の登録表示は同名の有無によるため、別の変換まで全部登録済みかどうかは表示だけで判断できません。

## 普段の作業

1. プロジェクト直下の `辞書追加アプリ.cmd` を開き、名前・読み・根拠を確認します。
2. 名前・読み・必要な別の変換を編集し、「追加する・あとで確認・追加しない」を選びます。入力と選択は作業記録へ自動保存されます。
3. 「追加予定の○件を確認」から内容を確認し、「候補DBに保存する」を押します。保留・見送りも候補DBに保存され、未確認の候補とメモは次の作業へ引き継がれます。
4. 辞書へ追加したいときは「辞書追加の依頼文をコピー」を押し、Codexへ依頼します。

依頼例：

> 候補DBに保存した追加予定を確認して、作業用ブランチで辞書に追加して。

自動保存済みの表示は、今の作業記録への保存を示します。Codexへ辞書追加を依頼する前に、候補DBへの保存まで完了してください。依頼文のコピーだけでは候補DBの保存・辞書への追加・Web公開は実行されません。

保存済みの追加予定は通常の未確認一覧から外れます。「追加予定をまとめて呼び出す」で見直せます。詳しい画面操作は [アプリの使い方](../tools/candidate-editor/アプリの使い方.txt) を参照してください。

## Codexが辞書へ追加するとき

1. 現在のブランチと未コミット変更を確認し、作業用ブランチを用意します。既存の編集内容を保持します。
2. 候補DBの主一覧・別管理候補と `candidate_editor_state.json` を識別IDで照合します。TSVとJSONの一致、採用判断、名前・読み・出典・本人の対応を確認します。作業中の `app_review.json` だけを確定済みの候補DBとして扱わないでください。
3. 採用候補の名前とフルネーム読みに加え、`extra_conversions` に保存された「読み・名前」も確認します。入力されていない短縮読みを自動で作りません。未確認・保留・見送りの候補は追加対象に含めません。
4. 各「読み・名前」を `data/master.tsv` と照合し、未登録の組み合わせだけを追加します。同じ名前でも別の読みがある場合は確認対象です。既存の読み・名前を、候補DBの編集だけで削除・置換しません。訂正や削除が必要な場合は内容と方針を別途確認します。
5. 追加する行の品詞を各IME向けに指定し、`origin=added`、`added_on=辞書への追加日`、`source_url=確認元URL`、必要な注記を記録します。候補DBへの保存日をそのまま辞書の追加日として扱わないでください。
6. `python scripts/build.py` と `python scripts/build_site.py` で配布4形式・追加記録・検索データ・ZIPを生成し、一致を確認します。READMEの追加内容・収録数も必要に応じて更新します。
7. 辞書関係の変更を作業ブランチにコミットします。公開する場合は、本番への反映と公開結果を別途確認します。詳細は [検索サイトの更新手順](SITE.md) を参照してください。

候補DBの「採用」は追加予定の判断として保持します。辞書反映済みかどうかは `master.tsv` との照合で確認し、次回の依頼でも同じ変換を重複追加しません。

## Excelの操作との関係

| 操作 | 更新するもの | 案内 |
| --- | --- | --- |
| ブラウザアプリ | 作業記録と候補DB | [アプリの使い方](../tools/candidate-editor/アプリの使い方.txt) |
| 元の候補台帳と `操作.ps1` | 候補DB。根拠・確認状態・本人情報なども編集できる | [候補編集のREADME](../tools/candidate-editor/README.txt) |
| 従来の「01→02→03」の日次Excel処理と `日々の操作.ps1` | 辞書本体・配布ファイル・ローカルサイトと候補DB | [毎日の使い方](../tools/candidate-editor/毎日の使い方.txt) |

日次Excel処理は、ブラウザアプリで保存した追加予定を辞書へ移すための操作ではありません。基本の手順はブラウザアプリで候補DBに保存し、Codexへ辞書追加を依頼する流れです。

日次Excelとアプリは `outputs/daily-dictionary/latest.json` を共有します。アプリへ引き継いだ一覧に日次Excelコマンドを実行すると止まります。作業中の記録を削除して切り替えず、元の操作で保存を完了してください。候補の調査・元台帳の反映・アプリの保存・辞書の追加は同時に実行せず、完了を確認して次へ進めます。

## 保存ファイルとバックアップ

| パス | 内容 |
| --- | --- |
| `outputs/vtuberpost_private/vtuberpost_readings.tsv`・`.json` | 主一覧。固定IDで候補を識別する |
| `outputs/vtuberpost_private/candidates_external.tsv`・`.json` | 別管理候補。`record_id` で候補を識別する |
| `outputs/vtuberpost_private/candidate_editor_state.json` | 採用・保留・見送りの判断、メモ、`extra_conversions` |
| `outputs/vtuberpost_private/candidate_editor_history.json` | 候補の変更前後と保存履歴 |
| `outputs/vtuberpost_private/candidate_manual_overrides.json` | 手動で確認・編集した主一覧の名前・読みを再結合時に保持する情報 |
| `outputs/daily-dictionary/latest.json` | 現在の作業一覧の場所 |
| `outputs/daily-dictionary/batches/<一覧ID>/app_review.json` | アプリの入力・選択・未確認候補の作業記録 |
| `outputs/daily-dictionary/batches/<一覧ID>/候補DB保存計画.json` | アプリの保存確認。`target=candidate_db` |
| `outputs/daily-dictionary/batches/<一覧ID>/完了.json` | 作業完了の記録。アプリの保存では `target=candidate_db`、`added_words=0` |
| `outputs/daily-dictionary/batches/<一覧ID>/backups/<ID>/` | アプリの候補DB保存、または従来の日次辞書反映の変更前後 |
| `outputs/vtuberpost_private/editor_backups/<日時_計画ID>/` | 元の候補台帳を候補DBへ反映した変更前後 |

バックアップの `manifest.json` で `status=applied` は対象ファイルへの保存完了、`rolled_back` は自動復元済みです。`applied` だけでは辞書反映やWeb公開の完了を意味しません。処理が強制終了した場合は保存計画・完了記録・バックアップの対象ファイルを照合します。

`outputs/` はGit管理から除外されます。候補DBや未保存の編集は、作業ブランチをコミットするだけでは保存・共有されません。このPCの候補DBとバックアップを保持してください。公開する辞書には、採用した名前・読みと公開の確認元だけを反映し、元資料や依頼者の連絡先を含めません。

## 開発者向けの処理の区別

- `Workspace.preview()` → `daily.preview_candidates()`：候補DBの保存内容を確認する。
- `Workspace.apply()` → `daily.save_candidates()`：候補DBだけに保存する。API名の `apply` は辞書への反映を意味しない。
- `daily.py preview/apply`：従来の日次Excel用の辞書反映処理。`辞書反映計画.json` を使う。
- `editor.py preview/apply`：元の候補台帳と候補DBの差分確認・反映処理。`反映計画.json` を使う。

アプリの候補DB保存計画を `daily.py apply` に渡すと、保存先が異なるため拒否されます。候補DB専用の保存に辞書のビルドを加えないでください。アプリの保存処理は、入力・候補DBの同時変更を確認し、辞書の更新とは分けて検証します。
